# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O projeto

**Empurrão**: jogo 3D casual de navegador, em terceira pessoa, para até 10 jogadores online. Cada jogador escolhe nome e cor e pode andar, correr, pular, bater, pescar na fonte da praça, cortar árvores com machado, negociar com o comerciante, comprar roupas com a Deendi, comprar ferramentas com o Gabriel, vender madeira ao Brenno na madeireira e jogar Tiro ao Alvo na barraca do Balotinho. **Não há vida nem dano**: o soco só empurra (knockback) e toca uma reação visual.

Stack: Vite + TypeScript 7, Three.js, Rapier (`@dimforge/rapier3d-compat`, character controller cinemático), `CSS2DRenderer` para os nomes, Node.js + Socket.IO no servidor e Playwright para E2E. **Não adicione dependências sem necessidade clara. Nada de React nem engines de jogo.**

## Comandos

```bash
npm install
npm run dev            # cliente (Vite, 5173) + servidor (tsx watch, 3000) via concurrently
npm run typecheck      # tsc --noEmit em shared, server, client e e2e (raiz)
npm run test:e2e       # Playwright; sobe o dev server sozinho se não estiver rodando
npx playwright test -g "soco"              # um teste só, pelo nome
npx playwright test --repeat-each=10       # caçar testes instáveis
npm run build && npm start                 # produção: um processo Node na porta $PORT (padrão 3000)
docker compose up -d --build               # produção em container (ver README para Portainer)
```

Na primeira vez: `npx playwright install chromium`.

**Sempre rode `npm run typecheck` após alterar código, e `npm run test:e2e` após mexer em rede, gameplay ou tela de entrada.** Não há linter configurado.

No Windows, parar o `npm run dev` (ou a tarefa em segundo plano) pode deixar os processos `vite` e `tsx` vivos nas portas 5173/3000; confira e encerre-os.

## Arquitetura

Monorepo com npm workspaces: `shared/`, `server/`, `client/`, além de `e2e/` na raiz.

### `shared/`: fonte única da verdade
- `protocol.ts`: tipos de **todas** as mensagens de rede (`ClientToServerEvents` / `ServerToClientEvents`, tipando o Socket.IO dos dois lados). Mensagem nova ou alterada vai aqui primeiro.
- `constants.ts`: todos os números de gameplay, rede, câmera e validação (velocidades, alcance e cooldown do soco, knockback, paleta `PLAYER_COLORS` etc.). **Nada de números mágicos espalhados.**
- `inventory.ts`: o inventário do jogador e o catálogo de **tudo** que se carrega (`INVENTORY_ITEMS`: nome, emoji e `stack`, quantas unidades empilham num espaço). São `INVENTORY_SLOTS` espaços (hoje 8; peixe e madeira empilham até 10, ferramentas ocupam 1 espaço cada). `Inventory` é a contagem por item; `canAdd` diz se cabe (espaços e `MAX_TOOLS`), `withItem` soma/tira e `inventorySlots` monta os espaços para a tela. Cheio = não cabe mais aquele item (uma pilha incompleta ainda aceita). Item novo: adicione aqui (e, se for vendido, em `items.ts` ou `tools.ts`).
- `items.ts`: itens que o comerciante compra e vende (`ITEMS`: preço de compra/venda em reais e estoque inicial/máximo dele); nome e emoji vêm do `inventory.ts`.
- `outfits.ts`: catálogo de roupas e acessórios da Deendi (`OUTFIT_ITEMS`: nome, emoji, parte do corpo `slot` e preço). Cada parte do corpo (`OUTFIT_SLOTS`) aceita **um** item por vez; comprar outro da mesma parte troca o atual (por isso cartola e boné não vão juntos). Item novo: adicione aqui e crie o modelo em `client/src/entities/wearables/wearableModels.ts` (o `Record` obriga). Parte do corpo nova: adicione em `OUTFIT_SLOTS`/`OUTFIT_SLOT_NAMES` e, se precisar de outro ponto de fixação, em `WearableAnchors` (`Character`).
- `tools.ts`: preço das ferramentas do Gabriel (`TOOL_ITEMS`) e `MAX_TOOLS` (quantas o jogador carrega ao mesmo tempo, hoje 2; pode repetir). Ferramenta nova: adicione em `inventory.ts`, aqui, e crie o modelo em `client/src/entities/tools/toolModels.ts` (o `Record` obriga).
- `math.ts`: convenção de ângulo `forwardFromYaw` (yaw 0 olha para +Z, igual ao `rotation.y` do Three.js). Cliente e servidor usam essa mesma função; o cone do soco no servidor depende dela.
- O pacote exporta os `.ts` direto (sem build). O Vite e o `tsx` os consomem como código-fonte; o build do servidor os empacota.

### Modelo de rede
- **Movimento com autoridade do cliente.** Cada cliente simula o próprio personagem e envia `state` a 20 Hz (`TICK_RATE`). O servidor (`Room.updateState`) limita deslocamentos impossíveis (`MAX_PLAUSIBLE_SPEED`) e prende a posição dentro do mapa, sem avisar o cliente.
- **Soco com autoridade do servidor.** O cliente manda só `punch {}`. `Room.punch` checa o cooldown e procura o alvo mais próximo no cone, usando as últimas posições e o `rotationY` conhecidos. Em caso de acerto, envia `hit` para todos. Só o cliente atingido aplica o knockback no próprio controller; os demais tocam a reação visual.
- **Tiro ao Alvo com autoridade do servidor sobre o dinheiro.** `server/src/ShootingBooth.ts` põe a barraca fora da praça, no maior vão entre bancos **sem** a placa (o do comerciante), de frente para a fonte, com o Balotinho num canto atrás do balcão (`SHOOTING_OWNER_OFFSET`). `ShootingGallery` guarda as partidas: `shootingStart {}` cobra `SHOOTING_ENTRY_COST` (perto do balcão e com saldo, via `Room.spendMoney`); cada `shootingShot { hit }` conta um acerto ou encerra a partida (erro, longe do balcão ou expirada); o `SHOOTING_TARGETS_TO_WIN`-ésimo acerto paga `SHOOTING_PRIZE` (`Room.earnMoney`). Tiro mais rápido que o `SHOOTING_SHOT_COOLDOWN_MS` (com folga) não conta, mas a resposta devolve o placar. Responde `money` e `shooting { phase, hits }` só ao jogador e, no fim, `shootingResult` a todos (o Balotinho mostra 🏆 ou 😜). `shootingStop {}` (sair no meio) e desconectar perdem a entrada.
- O servidor faz broadcast de `snapshot` a 20 Hz. O lobby é reenviado a **todos** os sockets (inclusive os que ainda estão na tela de entrada) sempre que alguém entra ou sai; ele alimenta as cores desabilitadas e o "X/10 online".
- **Inventário no servidor.** O inventário é o campo `inventory` do `PlayerSnapshot`. Tudo o que muda o inventário (pescar, dar peixe, negociar, comprar ferramenta, cortar árvore) é conferido no servidor (inclusive o espaço, com `canAdd`) e responde `inventory { inventory }` só ao jogador. Na reconexão, o `Network` reenvia o inventário no `join`; `parseInventory` descarta item desconhecido e quantidade inválida e só mantém o que couber.
- **Pesca com contagem no servidor.** O minigame roda no cliente; ao acertar, ele manda `fishCaught {}`. `Room.catchFish` só conta se o jogador estiver junto à fonte, respeitar `FISH_CATCH_COOLDOWN_MS` e tiver espaço para o peixe.
- **Cortar árvore com autoridade do servidor.** `server/src/Forest.ts` guarda as árvores (com `chopped`). O minigame roda no cliente; ao derrubar, ele manda `chopTree { treeId }`. `Forest.chop` confere machado no inventário, árvore em pé, distância (`CHOP_RANGE` + folga), `CHOP_COOLDOWN_MS` e espaço para `WOOD_PER_TREE` madeiras. Aí marca a árvore como toco, responde `inventory` e faz broadcast de `treeChopped` (todos trocam a árvore por um toco). Quem entra depois recebe os tocos no `welcome`. A árvore não volta a crescer; a madeira é vendida ao Brenno, na madeireira.
- **Dar peixe aos animais com autoridade do servidor.** A contagem de peixes é o inventário. O cliente manda `feedAnimal { animalId }`; o servidor só aceita gato ou cachorro (`FISH_EATING_ANIMALS`; cavalo não come), com peixe no inventário, dentro de `FEED_RANGE` (+ folga), respeitando `FEED_COOLDOWN_MS` e se o animal ainda não segue esse jogador. Aí desconta o peixe (`inventory` para o jogador), faz broadcast de `animalFed` (todos mostram o coração) e o animal passa a seguir o jogador (`followingId` no `AnimalSnapshot`) até outro lhe dar peixe ou o jogador sair.
- **Comerciante com autoridade do servidor.** `server/src/Merchant.ts` põe a barraca do lado de fora da praça, no maior vão ao lado da placa, olhando para a fonte, e guarda o estoque (`ITEMS[item].stock`). O cliente manda `trade { item, action }` (`buy`/`sell`, uma unidade, do ponto de vista do jogador); `Room.trade` confere distância até a mesa (`MERCHANT_TRADE_RANGE` + folga), `TRADE_COOLDOWN_MS`, dinheiro/item, espaço no inventário (comprar) e estoque/espaço do comerciante. Aí responde `inventory` e `money` ao jogador e faz broadcast de `merchantStock` (todos atualizam o estoque e o comerciante mostra 💰). O dinheiro é o campo `money` do `PlayerSnapshot` (reais, inteiro) e volta no `join` ao reconectar, como o inventário (validado entre 0 e `MAX_MONEY`). O comerciante não tem limite de dinheiro.
- **Loja de roupas com autoridade do servidor.** `server/src/ClothingShop.ts` põe a Deendi do lado da placa que o comerciante não usa (`signSides` em `Square.ts`). O cliente manda `buyOutfit { item }`; `ClothingShop.sell` confere distância até o balcão (`CLOTHING_SHOP_RANGE` + folga), `OUTFIT_BUY_COOLDOWN_MS`, se já veste o item e o saldo (`Room.spendMoney`), e veste (`Room.setOutfit`). Responde `money` e `outfit` ao jogador e faz broadcast de `outfitSold` (a Deendi mostra 🛍️). As roupas são o campo `outfit` do `PlayerSnapshot` (os remotos se vestem pelo snapshot) e voltam no `join` ao reconectar (`parseOutfit` descarta item desconhecido ou da parte errada).
- **Loja de ferramentas com autoridade do servidor.** `server/src/ToolShop.ts` põe o Gabriel no lado mais livre da praça (`quietestSide` em `Square.ts`: o ângulo mais longe da placa, dos bancos e das outras barracas; por isso é criada por último). O cliente manda `buyTool { item }`; `ToolShop.sell` confere distância até a bancada (`TOOL_SHOP_RANGE` + folga), `TOOL_BUY_COOLDOWN_MS`, espaço no inventário (`canAdd`, que também limita a `MAX_TOOLS`) e o saldo (`Room.spendMoney`), e guarda (`Room.setInventory`). Responde `money` e `inventory` ao jogador e faz broadcast de `toolSold` (o Gabriel mostra 🔨). O machado serve para cortar árvores; ainda não há como largar ou vender ferramentas.
- **Madeireira com autoridade do servidor.** `server/src/LumberMill.ts` põe o Brenno no lado mais livre que sobrar (`quietestSide`, criada depois do Gabriel, com a loja dele entre as barracas ocupadas). O cliente manda `sellWood { amount }` (inteiro ≥ 1); `LumberMill.buy` confere distância até o balcão (`LUMBER_RANGE` + folga), `WOOD_SELL_COOLDOWN_MS`, se o jogador tem essa madeira toda e se o dinheiro não passa de `MAX_MONEY`. Paga `WOOD_SELL_PRICE` por madeira (`Room.earnMoney`), tira a madeira (`Room.setInventory`), responde `money` e `inventory` ao jogador e faz broadcast de `woodSold` (o Brenno mostra 🪵). O Brenno não tem limite de compra.
- `validation.ts` valida tudo que chega como `unknown`: nome sanitizado (sem HTML, 1–16 caracteres), cor da paleta, `state` com números finitos e rate limit por "balde de fichas". O motivo de rejeição segue a ordem `full` → `invalidName` → `colorTaken`. Com a sala cheia, as 10 cores estão ocupadas, então o cliente envia `join` sem cor para receber `full`.
- Socket.IO só via websocket, na mesma origem. Em dev, o Vite faz proxy de `/socket.io` para a porta 3000; em produção, o servidor serve `client/dist` e o Socket.IO na mesma porta.
- **Reconexão:** `Network` guarda a sessão (nome + cor) e reenvia `join` a cada `connect`. Um novo `welcome` chega ao `Game` (o id muda), que recria os remotos e mantém a posição local. Um `joinRejected` durante o jogo volta à tela de entrada. Um `join` enviado antes de conectar fica no buffer do Socket.IO.
- A sala vive na memória do processo: **uma instância só**.

### Cliente
- `main.ts` → `JoinScreen` (só sai após `welcome`) → `Game`. O WASM do Rapier (`Physics.init()`) carrega em paralelo, enquanto o jogador preenche o formulário.
- `Game.loop` (requestAnimationFrame), em ordem:
  1. `Input.consume()` gera intenções; os handlers de input **nunca** mexem no jogo. `Interactions.update` trata a Ação (ou o `Game` soca).
  2. Câmera gira (depois da Ação, para o tiro valer contra a tela já desenhada) e converte o WASD para direção no mundo.
  3. `RemotePlayers.update` interpola e posiciona os colliders cinemáticos.
  4. Física em passo fixo de 60 Hz com acumulador: `LocalPlayer.preStep` → `physics.step` → `postStep`.
  5. Renderização interpolada (`alpha` do acumulador).
  6. Envio do `state` a 20 Hz.
- **Posições na rede e na malha são dos pés** (y = 0 no chão). O corpo do Rapier é uma cápsula centrada em `CAPSULE_CENTER_Y` acima dos pés.
- A gravidade é manual no `LocalPlayer` (o mundo Rapier tem gravidade 0). O knockback é uma velocidade horizontal que decai (`KNOCKBACK_DAMPING`) somada ao input. O personagem gira para a direção do **movimento**, não da câmera, e só gira enquanto anda.
- **Remotos:** buffer de estados com o horário convertido para o relógio local (estimativa de offset em `RemotePlayers.applySnapshot`), renderizados `INTERPOLATION_DELAY_MS` no passado; nunca teleportam. A animação de soco remota dispara na transição do `anim` para `"punch"`.
- **Botão de Ação (F, clique ou botão de toque):** é contextual. Cada sistema implementa `ActionHandler` (`game/ActionResolver.ts`: `active`, `actionLabel()`, `act()`) e o `ActionResolver` escolhe: quem estiver `active` (minigame/painel aberto) fica com a Ação; senão, o primeiro da lista com rótulo. A lista e a ordem ficam em `game/Interactions.ts` (que monta os controladores e os liga à HUD): Negociar/Fechar → Comprar roupas/Fechar → Comprar ferramentas/Fechar → Vender madeira/Fechar → Jogar/Atirar → Dar peixe → Cortar árvore/Golpear → Pescar/Fisgar; se ninguém quiser, `Interactions.update` devolve false e o `Game` soca ("Bater"). Sistema novo: implemente `ActionHandler`, adicione o rótulo em `ACTION_LABELS` e coloque-o na lista. A HUD mostra o rótulo no computador; no celular, quem muda é o texto do próprio botão.
- **Dar peixe:** `FeedingController`: com peixe no inventário e de frente para um gato/cachorro perto (`AnimalsManager.feedTarget`), a Ação vira "Dar peixe". O coração é o `Animal.playHeart` (mesma animação das reações). A IA de seguir roda no servidor (`AnimalAgent.follow`).
- **Pesca:** `FishingMinigame` é só lógica (marcador que vai e volta numa barra; acertar a área verde = peixe), `FishingPanel` é o DOM e `FishingController` liga tudo. A dificuldade vem de `fishingDifficulty(contagem)`: marcador mais rápido e área menor a cada peixe. Pescando, o `LocalPlayer` fica parado com `stance = "fish"` (a `anim` vira `"fish"`), que mostra a vara (`entities/FishingRod.ts`) também nos remotos. Sai-se com Q, Esc, soltando o mouse, o botão Sair ou andando/pulando. Com o inventário cheio, a Ação só mostra "🎒 Inventário cheio!" (`Hud.notify`) e o minigame fecha se encher no meio.
- **Inventário:** `game/PlayerInventory.ts` guarda o inventário que o servidor mandou e avisa os inscritos (`onChange`: HUD e painéis das lojas). A HUD mostra sempre a barra de espaços (`ui/InventoryBar.ts`, abaixo do dinheiro), vermelha quando todos os espaços estão ocupados. Pesca, corte e lojas conferem `canAdd` antes de agir; sem espaço, mostram "Inventário cheio" e não enviam nada.
- **Cortar árvore:** `ChoppingMinigame` é só lógica (marcador que vai e volta; cada Ação na área amarela é um golpe; `CHOP_HITS_TO_FELL` golpes derrubam, `CHOP_MAX_MISSES` erros e o machado escorrega), `ChoppingPanel` é o DOM e `ChoppingController` (um `ActionHandler`) liga tudo: com machado e de frente para uma árvore em pé (`TreesManager.chopTarget`), a Ação vira "Cortar árvore" e, no minigame, "Golpear". Cortando, `stance = "chop"`: o machado aparece erguido também nos remotos, e cada golpe certo toca `Character.playChop` e balança a árvore (`TreesManager.shake`, só no cliente). A vara, a espingarda e o machado na mão ficam em `entities/HeldItems.ts`.
- **Celular:** `isTouchDevice()` (`pointer: coarse`) decide o modo. No celular, `TouchControls` cria analógico (inclinar até a borda = correr), botões Pular/Ação e arrastar a tela para girar a câmera; o `Input` mescla essas intenções com as do teclado e não usa pointer lock. A `Hud` só mostra a ajuda de teclado no computador; no celular não há ajuda de controles.
- **Música:** `Music.ts` compõe e sintetiza um loop com Web Audio (sem arquivos de áudio). O `AudioContext` só é criado no primeiro gesto do usuário (já na tela de entrada); tecla M ou botão 🎵 da HUD liga/desliga (lembrado no `localStorage`) e a música pausa com a aba oculta.
- **Árvores:** o servidor sorteia `TREE_COUNT` árvores ao iniciar (`server/src/Trees.ts`: tipo, posição longe do centro e das outras, escala entre `TREE_MIN_SCALE` e `TREE_MAX_SCALE`) e as envia no `welcome`. No cliente, `TreesManager` cria a malha e um cilindro fixo do Rapier (o jogador colide; o servidor e os animais não sabem delas). Árvore derrubada vira `entities/trees/Stump.ts` (toco com lascas), com um colisor mais baixo. Tipo novo: adicione em `TREE_TYPES` (protocolo), crie a subclasse de `entities/trees/Tree.ts` e registre em `TREE_FACTORIES`.
- **Praça:** o servidor gera **exatamente uma** praça ao iniciar (`server/src/Square.ts`), antes das árvores, que evitam a área dela. Ela fica entre `SQUARE_MIN_DISTANCE` e `SQUARE_MAX_DISTANCE` do centro, com 2–5 bancos virados para a fonte, uma placa com `SQUARE_SIGN_TEXT` na borda virada para o centro do mapa e uma fonte com 2–5 peixes (cada um com tamanho diferente). Vai no `welcome` como `square`. **Todos nascem na praça:** `Room.findSpawn` sorteia um ponto no anel entre `SPAWN_MIN_DISTANCE` (fora do alcance da pesca) e `SPAWN_MAX_DISTANCE` (antes dos bancos), longe dos outros jogadores e de frente para a fonte; quem cai do mapa volta ao ponto onde nasceu. No cliente, `SquareManager` monta os modelos de `entities/square/` e os colisores (fonte, coluna, bancos e placa). O `Fountain` contém os peixes; o nado (`Fish.update`) roda **só no cliente**, por ser decorativo, então a posição dos peixes não é igual entre jogadores.
- **Comerciante:** vem no `welcome` como `merchant`. `MerchantManager` monta o `Character` com a aparência do servidor, a barraca (`entities/merchant/MerchantStall.ts`: mesa com a placa `MERCHANT_SIGN_TEXT`, caixote e toldo) e os colisores (mesa e comerciante). `MerchantController` decide se dá para negociar (de frente para a mesa) e abre o `MerchantPanel` (DOM); de frente para a mesa a Ação vira "Negociar" e, com o painel aberto, "Fechar". Ao abrir, o `Input.releasePointerLock` solta o mouse (sem contar como "sair") para clicar em Comprar/Vender. Fecha com Q, Esc, Sair, Ação ou andando. A HUD mostra sempre "💰 R$ N".
- **Loja de roupas:** vem no `welcome` como `clothingShop`. `ClothingShopManager` monta a Deendi (`CLOTHING_SELLER_APPEARANCE`, que veste os próprios produtos via `appearance.outfit`), a barraca (`entities/clothing/ClothingStall.ts`: balcão com placa, manequins com os produtos, arara e toldo) e os colisores. `ClothingController` (um `ActionHandler`, também guarda o `outfit` do jogador): de frente para o balcão a Ação vira "Comprar roupas" e abre o `ClothingPanel` (itens agrupados por parte do corpo: Comprar/Trocar/Comprado). As roupas são montadas pelo `Wardrobe` do `Character` (`entities/wearables/`), que troca só a parte que mudou e libera os recursos da peça antiga.
- **Loja de ferramentas:** vem no `welcome` como `toolShop`. `ToolShopManager` monta o Gabriel (`TOOL_SELLER_APPEARANCE`), a barraca (`entities/tools/ToolStall.ts`: bancada com placa, painel com ferramentas penduradas, tora com machado cravado e toldo) e os colisores (bancada, painel, tora e Gabriel). `ToolShopController` (um `ActionHandler`): de frente para a bancada a Ação vira "Comprar ferramentas" e abre o `ToolShopPanel` (o botão fica desabilitado sem espaço no inventário ou no limite de ferramentas). Os modelos das ferramentas (`entities/tools/toolModels.ts`) recebem um `ToolKit` (ex.: `WornItem`) e servem para a barraca e para a mão do jogador.
- **Madeireira:** vem no `welcome` como `lumberMill`. `LumberMillManager` monta o Brenno (`LUMBER_BUYER_APPEARANCE`, com bigode), a barraca (`entities/lumber/LumberStall.ts`: balcão de tábuas com placa, pilha de toras, cavalete com serra circular e toldo) e os colisores (balcão, pilha, serra e Brenno). `LumberMillController` (um `ActionHandler`): de frente para o balcão a Ação vira "Vender madeira" e abre o `LumberMillPanel` ("Vender 1" e "Vender tudo"; sem madeira, os botões desabilitam e o painel lembra que o Gabriel vende o machado).
- O cenário do `welcome` (árvores, praça, comerciante, Tiro ao Alvo, loja de roupas, loja de ferramentas, madeireira) é montado e recarregado junto pelo `game/Scenery.ts`.
- **Tiro ao Alvo:** vem no `welcome` como `shootingBooth`. `ShootingBoothManager` monta o Balotinho (`Character` com `SHOOTING_OWNER_APPEARANCE`), a barraca (`entities/shooting/ShootingStall.ts`: balcão com espingardas, toldo, placa `SHOOTING_SIGN_TEXT` com lâmpadas e dois trilhos de `Duck`) e um colisor que cobre o balcão e o interior. Os patos andam **só no cliente** (decorativos, como os peixes); ao levar tiro tombam até dar a volta no trilho. `ShootingController` (um `ActionHandler`): de frente para o balcão a Ação vira "Jogar (R$ 1)"; sem saldo, a HUD avisa (`Hud.notify`) e nada é enviado. Ao receber `shooting { phase: "playing" }`, o jogador fica com `stance = "aim"` (pose com a espingarda, `entities/AirRifle.ts`, também nos remotos), a câmera entra no modo de mira (`ThirdPersonCamera.aiming`: mais perto e por cima do ombro direito) e o `ShootingPanel` mostra a mira no centro da tela. A Ação vira "Atirar": o raio sai do centro da tela (`ShootingBoothManager.shoot`) e a primeira coisa atingida decide (pato em pé = acerto; barraca, Balotinho ou nada = erro). O tiro é resolvido **antes** de girar a câmera e de os patos andarem no frame, contra o que estava na tela. Sai-se com Q, Esc, Sair, andando ou sendo empurrado (perde a entrada).
- Modelos estáticos de primitivas (árvores, objetos da praça) herdam de `entities/Model.ts`, que registra geometrias, materiais e texturas para o `dispose()`.
- `Character.ts` monta a pessoa com primitivas e faz todas as animações procedurais (parado, andar, correr, pulo, soco e atingido). Recebe só a cor (jogadores) ou uma `CharacterAppearance` (protocolo) com calça, pele, chapéu (`cap`, `wide`, `boater`), avental, colete, gravata-borboleta e bigode (`CharacterAccessories.ts`); as dos NPCs são `MERCHANT_APPEARANCE`, `SHOOTING_OWNER_APPEARANCE`, `CLOTHING_SELLER_APPEARANCE`, `TOOL_SELLER_APPEARANCE` e `LUMBER_BUYER_APPEARANCE`. Roupas compradas: `Character.setOutfit`. O nome e a bolha de reação ficam em `NameTag.ts`. Recursos do Three.js precisam de `dispose()` ao remover um personagem, incluindo o elemento DOM do rótulo.

### Testes E2E e API de debug
- Em modo dev (`import.meta.env.DEV`), o `Game` expõe `window.__jogo` (montada por `createDebugApi`) com `selfId`, `local`, `remotes`, `lookAt`, `trees`, `square`, `fishing` (o `label` é o rótulo atual da Ação), `animals`, `merchant`, `shooting`, `clothing`, `tools`, `lumber`, `inventory`, `chopping`, `aimAt` (aponta a mira para um ponto; com um `keydown` de F no mesmo `evaluate`, o tiro acerta onde mirou), `rejoin` (reconecta reenviando dinheiro/inventário no `join`, que o servidor valida; é como os testes de interface ganham um machado ou enchem o inventário) e `teleport` (põe o jogador num ponto; o servidor só alcança a posição nova aos poucos, por causa do limite de velocidade) (interface em `game/DebugApi.ts`). Os testes dependem dela; os tipos estão duplicados em `e2e/global.d.ts`, mantenha os dois em sincronia. Ela não existe no build de produção.
- **O `CSS2DRenderer` só insere o rótulo de nome no DOM quando o personagem está na frente da câmera.** Não use `.name-label` para checar se um jogador existe; use `__jogo.remotes()`.
- Os testes compartilham uma sala real: rodam com `workers: 1`, esperam a sala esvaziar no `beforeEach` e fecham os contextos no fim. O teste de "sala cheia" usa 10 bots `socket.io-client` em Node, sem navegador.
- WebGL headless usa SwiftShader (flags no `playwright.config.ts`).

## Convenções

- TypeScript `strict` + `noUncheckedIndexedAccess`; **sem `any`** (use `unknown` + validação). Imports com `moduleResolution: bundler`; no servidor, os imports relativos usam o sufixo `.js`.
- Um arquivo por classe ou sistema, **no máximo ~300 linhas**; se passar disso, divida.
- Comentários e textos da interface em **português**; nomes de código em inglês.
- Logs do servidor curtos (entrada, saída, rejeição, início/fim). Nada de log por frame.
- Three.js 0.186: `PCFSoftShadowMap` foi removido (use `PCFShadowMap`).

## Como verificar mudanças visuais ou de gameplay

O typecheck não pega bugs de 3D. Depois de mudanças visuais ou de gameplay:
1. Rode `npm run dev` e abra `http://localhost:5173` com Playwright, usando um script descartável que importe `@playwright/test` de `node_modules`.
2. Entre com nome e cor, tire um screenshot e confira chão, personagem, nome e câmera.
3. Leia o console do navegador e corrija erros e warnings.
4. Para multiplayer, abra duas abas (contextos separados) e confira movimento e soco.

O pointer lock (câmera pelo mouse e soco por clique) não funciona no headless; teste o soco pela tecla F.
